## Последовательность действий

1. Развертываем локально Keycloak 26.*.*
2. Импортируем туда тестовые realm из папки keycloak в проекте
3. Для работы с проектом необходим запущенный сервер Keycloak
4. Создаем в Postgres локальную базу данных webflux, схема public
5. Актуализируем подключения к БД в application.properties
6. Запускаем Spring Boot приложение, включаем liquibase
7. Проверяем коллекцией в папке postman


## Описание запросов POSTMAN

` GET /webflux/customer/7bdd9088-29b2-4fa8-9c3d-bf539ecb825a `

- имитирует синхронный запрос с WEB для получения информации пользователя, который предоставляет сторонний сервис методом callback
- запрос в сторонний сервис не выполняется, но подразумевается что он выполнен, и нам нужно ждать callback с признаком USER_INFO для пользователя, который задан идентификаторов в запросе
- ожидание ограничено параметром TIMEOUT, заданным в конфигурации приложения. Если в течение этого времени (параметр задается в секундах) не будет получен ответ, метод вернет статус 408 и сообщение о произошедшем тайм-ауте
- для ожидания callback - метод с задержкой в 1 секунду (hardcoded) проверяет БД на существование поступившего ответа от стороннего сервиса
- как только будет найден ответ (раньше чем тайм-аут) - метод вернет информацию пользователя и очистит таблицу БД от прочитанной записи (или записей)

` POST /webflux/customer/callback `

- имитирует callback ответ стороннего сервиса
- этот запрос передает в теле сущность, которую ждет первый метод
- при обработке запроса, в БД делается запись, которую как описано выше ждет синхронный неблокирующий метод GET
- для проверки вы можете сделать сразу несколько callback, чтобы создать несколько записей сразу, и проверить как метод GET выберет для себя только последний и удалит все callback по признаку USER_INFO для заданного пользователя


` GET /webflux/mono/customer/{user_id} (3 запроса с разными идентификаторами) `

- можно имитировать сразу 3 запроса клиента для получения информации пользователя по разным идентификаторам
- для исполнения запросов выполняется ожидание возвратных запросов от стороннего сервиса
- поэтому, чтобы закончить эти методы, выполните соответствующие callback запросы (смотри ниже)

` POST /webflux/mono/customer/callback `

- выполните эти запросы, чтобы завершить запросы клиента описанные выше

` GET /webflux/private/token-info `

- имитирует аутентифицированный запрос с токеном в контроллер
- возвращает сущность AccessToken пользователя, для которого подписан токен

` GET /webflux/admin/token-info `

- имитирует авторизированный запрос с токеном в контроллер
- Для доступа к endpoint необходима обязательная роль ADMIN
- возвращает сущность AccessToken пользователя, для которого подписан токен

## Вход на тестовую WEB страницу

` http://localhost/webflux/index `

- в realm SpringBootKeycloak есть пользователи, их password = username
- есть модифицированный поток аутентификации (все фичи в нем исключительно исследовательские)
- если пользователь имеет роль admin - ему не надо будет вводить password (просто фича)
- если пользователь имеет тип 2FA = SMS - ему нужно ввести 4-значный код (stub 1111)
- в настройках потока, можно отключить имитацию и смотреть код СМС в логах Keycloak (не забудьте --verbose при старте сервера)
- если пользователь имеет 2FA = APP - требуется второй фактор через google authentication. Уже настроенные в realm пользователи с APP будут просить OTP у меня, поэтому для проверки создайте нового с APP и сможете проверить работу
- в потоке есть маргинальный limiter, который блокирует вход списку пользователей. Сейчас там один пользователь: nikola
